# PP16 1.1 - gradient dither development scope

Status: gradient/dither painting is implemented on `v1.1`, following the
successful Medium compatibility trial. Medium is now the development default;
version 1.0 remains the stable Small distribution. See
[the implementation record](GRADIENT-DITHER.md) for gestures and validation.

## Preserve the 1.0 release

`main` contains release commit `4a2299e` and the frozen installation files in
`dist/PP16V10/` plus `dist/PP16V10.ZIP`. See [the distribution record](../dist/README.md).
Do not rebuild or replace those files with version 1.1 binaries. The accepted
packed-buffer Clear improvement is part of 1.0 and must remain working.

## Agreed interaction

- Compress the existing lower-left 16-colour palette vertically to make room
  for a permanent gradient selector beneath it, following the user's drawing.
- Provide two dedicated endpoint-colour boxes, with a horizontal dither ramp
  between them. Keep the controls in the main panel rather than a popup.
- Mouse selection along the ramp chooses a mixture in 10% increments, from
  the first endpoint to the second. Show a selection marker and a readable
  percentage.
- A selected mixture replaces the active brush paint. Show its dither pattern
  in the existing foreground/brush-colour display. There is no need to save
  or restore the previous active solid colour.
- Selecting an ordinary palette colour selects solid paint again. Retain the
  endpoint colours and mixture setting so the ramp remains usable.
- Apply the selected paint to Brush, Line, Circle, Square, Bucket Fill and
  Clear to Colour. Keep ordinary Clear and Alt+C as fast black clears.
- Anchor dither patterns to image coordinates so overlapping strokes align,
  and use the same pattern resolution for shape previews and committed pixels.

The result is ordinary 16-colour image pixels, not additional hardware colours.
Native P16/CLP formats, undo and literal clipboard contents can stay compatible.
A single pixel still has one endpoint colour; the perceived mixture spans
multiple pixels. Click an endpoint box and then a palette colour to assign it.
The ordered 10x10 tile has exact coverage in 10% steps; the foreground swatch
and percent readout identify selected gradient paint. The user approved the
rendered layout during implementation.

## Implementation constraints

The 1.0 baseline has 64,532 linked code bytes, leaving 1,004 bytes below the
small-model code limit. Its data group, including the 8 KiB stack, occupies
57,728 bytes; recorded startup `MemAvail` is 7,810 bytes. These are release
measurements; current gradient-build measurements are in the implementation
record linked above.

`TPaint` provides one shared resolver for painting paths and previews.
`DocSetPixel` remains literal so clipboard and file pixels are preserved.
Bucket Fill uses a 512-byte visited map because a mixture can leave old-colour
pixels unchanged. Clear to Colour copies packed pattern rows and uses the
full-image scanline redraw, preserving the fast solid-fill path and
no-change/undo behaviour.

## Medium-model compatibility trial

The user authorized testing the current editor under `-WmMedium` before
adding gradient paint. The separate target uses matching FPC 3.2.2 runtime
units built from release sources, model-dependent `CodePointer` exit hooks,
and isolated object/output directories. Full regression and production
Save/Open pass under DOSBox-X. See [setup, measurements and evidence](MEDIUM-MODEL.md).

Medium permits multiple code segments while keeping the near-data group
limited to 64 KiB. Measured code is 67,804 bytes; startup near heap is 7,662
bytes. Rendering matches the Small baseline byte for byte in the regression
captures. That compatibility checkpoint kept Small as default. Gradient
development now defaults to Medium; the packaged 1.0 files are unchanged.
Interactive acceptance and actual HX timing remain separate from emulator
validation before adopting Medium for a release.

A custom virtual-memory/overlay manager is not selected. Paging data alone
does not remove the code-segment limit; code overlays would be a broader
architecture change. EMS or disk-backed image storage may be useful if later
work introduces collections of frames. The current work covers gradient paint
following the Medium compatibility trial; a virtual-memory system is not part
of it.
