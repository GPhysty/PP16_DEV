# PP16 1.1 - gradient dither development scope

Status: design agreed in principle; no gradient implementation or memory-model
migration has been made. The current branch is `v1.1`. Version 1.0 is the
stable distribution; version 1.1 is the next development version.

## Preserve the 1.0 release

`main` contains release commit `4a2299e` and the frozen installation files in
`dist/PP16V10/` plus `dist/PP16V10.ZIP`. See [the distribution record](../dist/README.md).
Do not rebuild or replace those files with version 1.1 binaries. The accepted
packed-buffer Clear improvement is part of 1.0 and must remain working.

## Agreed interaction

- Compress the existing lower-left 16-colour palette vertically to make room
  for a permanent gradient selector beneath it, following the user's drawing.
- Provide two dedicated endpoint-colour boxes, with a horizontal dither ramp
  between them. Keep the controls in the main panel rather than a popup.
- Mouse selection along the ramp chooses a mixture in 10% increments, from
  the first endpoint to the second. Show a selection marker and a readable
  percentage; exact placement is still to be settled.
- A selected mixture replaces the active brush paint. Show its dither pattern
  in the existing foreground/brush-colour display. There is no need to save
  or restore the previous active solid colour.
- Selecting an ordinary palette colour selects solid paint again. Retain the
  endpoint colours and mixture setting so the ramp remains usable.
- Apply the selected paint to Brush, Line, Circle, Square, Bucket Fill and
  Clear to Colour. Keep ordinary Clear and Alt+C as fast black clears.
- Anchor dither patterns to image coordinates so overlapping strokes align,
  and use the same pattern resolution for shape previews and committed pixels.

The result is ordinary 16-colour image pixels, not additional hardware colours.
Native P16/CLP formats, undo and literal clipboard contents can stay compatible.
A single pixel still has one endpoint colour; the perceived mixture spans
multiple pixels. The endpoint assignment gesture, pattern tile, exact coverage
ratios and solid/mixture indication need final design decisions.

## Implementation constraints to investigate

The 1.0 baseline has 64,532 linked code bytes, leaving 1,004 bytes below the
small-model code limit. Its data group, including the 8 KiB stack, occupies
57,728 bytes; recorded startup `MemAvail` is 7,810 bytes. These are release
measurements, not a measured budget for the unimplemented gradient feature.

Keep one shared paint resolver for the painting paths and previews. Do not
globally reinterpret every `DocSetPixel` call: clipboard paste and other paths
must still write their literal pixel colours. Bucket Fill currently uses
changed pixel colours to prevent repeat visits. A dither mixture can leave
pixels unchanged, so this assumption must be replaced; one possible solution
is a 512-byte visited map for the 64x64 document. Clear to Colour should build
packed pattern rows and use full-image scanline redraw, preserving the fast
solid-fill path and no-change/undo behaviour.

## Medium-model option to retain for discussion

For continued feature growth, evaluate an isolated `-WmMedium` build of the
current editor before committing to migration. The installed compiler accepts
that option. Matching medium-model Pascal runtime units are needed; the
project currently installs its units under `8086-small`, although startup
objects for the other models are present.

Medium model permits multiple code segments while keeping the near-data group
limited to 64 KiB. Review explicit `NearCsPointer` exit hooks in the program
and test launchers, procedure callbacks and assembler calling conventions.
Compare brush, shape-preview and clear behaviour/timing against 1.0 and run
the existing focused and complete regressions before accepting a migration.
Actual HX timing remains separate from DOSBox measurements.

A custom virtual-memory/overlay manager is not selected. Paging data alone
does not remove the code-segment limit; code overlays would be a broader
architecture change. EMS or disk-backed image storage may be useful if later
work introduces collections of frames. This release-packaging task does not
authorize implementing any of those architecture changes.
